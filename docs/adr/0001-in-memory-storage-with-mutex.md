# Данные хранятся в памяти, двойную запись запрещает Mutex

Брони и типы встреч живут в памяти процесса, база данных не используется: приложение учебное, без авторизации, и постоянное хранилище добавило бы инфраструктуру без пользы для сценария. Проверка пересечения и вставка брони выполняются в `BookingRepository` атомарно под `Mutex` из coroutines, поэтому два одновременных запроса на один слот дают один `201` и один `409 SLOT_TAKEN`.

## Considered Options

- **База данных.** Данные пережили бы перезапуск, а правило «нет пересечений» держалось бы транзакцией или ограничением. Отклонено: требует отдельного сервиса, миграций и настройки деплоя.
- **Проверка и вставка раздельно.** Проще, но при одновременных запросах оба проходят проверку и занимают один слот. Отклонено: нарушает главное правило приложения.

## Consequences

- Все данные теряются при перезапуске или засыпании сервиса на хостинге. Это записано в README.
- `Mutex` защищает только один процесс. Второй экземпляр приложения получил бы своё хранилище и не видел чужих броней, поэтому приложение запускается в одном экземпляре.
