# Архитектурные решения бэкенда

- Clean Architecture, каждый слой — отдельный Gradle-модуль в `backend/`, зависимости направлены внутрь:
  - `domain` — сущности и правила (тип встречи, бронь, интервал, расчёт слотов и пересечений), без зависимостей от Ktor и библиотек.
  - `application` — use case'ы в виде команд и запросов (CQRS), порты (интерфейсы репозиториев и `Clock`).
  - `infrastructure` — реализации портов (хранилище в памяти, системные часы).
  - `presentation` — Ktor-роуты, DTO под контракт, маппинг ошибок в HTTP-статусы, сборка DI. Точка входа приложения, к нему подключён плагин `application`.
  - Зависимости модулей: `application` → `domain`; `infrastructure` → `application`, `domain`; `presentation` → все остальные. `domain` ни от чего не зависит.
- Корневой пакет — `ru.hexlet.booking`, подпакеты по слоям: `domain`, `application`, `infrastructure`, `presentation`. Wrapper Gradle закоммичен. `presentation` слушает порт 8080 и отвечает `200` на `/api/health`.
- CQRS (в одном процессе, без event sourcing и общей шины):
  - команды (изменяют состояние): создать тип встречи, создать бронь; запросы (только читают): данные владельца, список типов, свободные слоты, предстоящие встречи.
  - базовые интерфейсы `CommandHandler<C, R>` и `QueryHandler<Q, R>`.
  - у каждой команды и запроса свой интерфейс обработчика, наследующий базовый, и одна реализация. Пример: `interface CreateBookingHandler : CommandHandler<CreateBookingCommand, Booking>` и `class CreateBookingHandlerImpl : CreateBookingHandler`. Роуты и DI зависят от интерфейса, а не от реализации.
  - роуты вызывают конкретные обработчики напрямую, медиатор не нужен.
- Реализация через интерфейсы: каждый порт (`MeetingTypeRepository`, `BookingRepository`, `OwnerProvider`, `Clock`) объявлен интерфейсом в `application`, реализация лежит в `infrastructure`. Зависимости передаются через конструктор.
- Данные владельца (имя, подпись, URL аватара) задаются в `application.conf` и читаются через порт `OwnerProvider`. Поле `timezone` в `GET /api/owner` — часовой пояс расписания (см. [schedule.md](schedule.md)).
- DI: Koin (`koin-ktor`), модули по слоям. Тесты подменяют модули или собирают объекты вручную.
- Хранилище: в памяти процесса, `BookingRepository` с `Mutex` из coroutines. Проверка пересечения и вставка выполняются атомарно в одной критической секции, поэтому два одновременных запроса не займут один слот.
- Время: интервалы хранятся как `Instant` с полуинтервалами `[start, end)`.
- `Clock` внедряется через зависимости, чтобы тесты окна в 14 дней не зависели от текущей даты.
- HTTP-статусы и коды ошибок описаны в [api.md](api.md#ошибки). `presentation` переводит доменные ошибки в них с соблюдением порядка проверок из [api.md](api.md#порядок-проверок).
- Паттерны имени, email и телефона в Kotlin повторяют `@pattern` контракта; тест сверяет их с `typespec/openapi.yaml`.
