# API и генерация клиента

Обязательная часть работы с API: TypeSpec-контракт, сгенерированная OpenAPI-спецификация и клиентский SDK для фронтенда.

- Цепочка: `typespec/main.tsp` → `tsp compile` → `typespec/openapi.yaml` (OpenAPI 3.1.0) → `@hey-api/openapi-ts` → SDK в `frontend/src/api/generated/`.
- Для языка фронтенда (TypeScript) генератор клиента из OpenAPI существует (`@hey-api/openapi-ts`), это проверено до выбора стека.
- Серверный генератор не используется: бэкенд на Ktor реализуется вручную по контракту и проверяется тестами на `testApplication`, которые покрывают сценарии контракта: каждый случай из колонки «Когда» таблицы [ошибок](#ошибки) на каждом эндпоинте, где статус указан в колонке «Ошибки», и каждый шаг [порядка проверок](#порядок-проверок), включая ошибки на двух шагах сразу (возвращается первая). Примеров ошибочных ответов в контракте нет.
- `openapi.yaml` коммитится в репозиторий. SDK генерируется скриптом `pnpm generate` (`mise run sdk`) и не коммитится: `frontend/src/api/generated/` добавлен в `.gitignore` и исключён из ESLint и Prettier. Компоненты импортируют клиент только оттуда.
- Источник правды по полям, ограничениям и примерам — `typespec/main.tsp`. Этот файл описывает правила, которые из контракта не видны или которые нужно соблюдать в бэкенде и фронтенде одинаково.

## Эндпоинты

Все пути начинаются с `/api`. operationId — по умолчанию TypeSpec (`Интерфейс_операция`), из него hey-api строит имена SDK: `meetingTypesListSlotsOptions`, `bookingsCreateMutation`, `getOwnerOptions` и т. д.

| Метод | Путь | operationId | Ответ | Ошибки |
| --- | --- | --- | --- | --- |
| `GET` | `/api/health` | `getHealth` | `{ status: "ok" }`, для smoke-теста | |
| `GET` | `/api/owner` | `getOwner` | `Owner`: `name`, `title` (подпись), `avatarUrl` (`null`, если нет), `timezone` (IANA, `Asia/Almaty`) | |
| `GET` | `/api/meeting-types` | `MeetingTypes_list` | `MeetingType[]`: `id`, `title`, `description`, `durationMinutes` | |
| `POST` | `/api/meeting-types` | `MeetingTypes_create` | `201 MeetingType` (владелец) | `400` |
| `GET` | `/api/meeting-types/{id}/slots` | `MeetingTypes_listSlots` | `Slot[]`: только свободные слоты `{ start, end }` на всё окно записи, по возрастанию `start`; занятые не возвращаются | `404` |
| `POST` | `/api/bookings` | `Bookings_create` | `201 Booking` | `400`, `404`, `409` |
| `GET` | `/api/bookings/upcoming` | `Bookings_listUpcoming` | `Booking[]`: предстоящие брони всех типов (владелец) | |

- `GET /api/meeting-types/{id}` нет: фронтенд берёт тип встречи из списка (см. [frontend.md](frontend.md#маршруты-и-экраны)). `GET /api/bookings/{id}` тоже нет: страница подтверждения показывает бронь из ответа `201`.
- `id` в пути `slots` — UUID. Значение, которое не разбирается как UUID, бэкенд трактует как несуществующий тип: `404 MEETING_TYPE_NOT_FOUND`.
- Пагинации нет ни в одном списке.

## Время

- Моменты времени передаются как `utcDateTime`: ISO 8601 в UTC с `Z` (`2026-11-02T04:00:00Z`). На фронтенде это `string`, трансформер дат hey-api не включён.
- Часовой пояс владельца отдаёт `GET /api/owner` в поле `timezone`. В нём фронтенд показывает время и группирует слоты по дням.
- Слот и бронь — полуинтервалы `[start, end)`. `end` вычисляет сервер как `start + durationMinutes`, клиент его не присылает.

## Тип встречи

- `id` генерирует сервер (UUID). Владелец задаёт поля `CreateMeetingTypeRequest`:
  - `title` — обязательная строка, 1–100 символов;
  - `description` — обязательная строка, до 1000 символов, пустая допустима;
  - `durationMinutes` — целое число минут, 15–540. Кратность шагу стартов не требуется, правила размещения слота — в [schedule.md](schedule.md).
- Любое нарушение — `400 VALIDATION_ERROR`.

## Бронь

`POST /api/bookings` принимает `meetingTypeId`, `start`, `guestName`, `guestEmail`, `guestPhone` и необязательное `notes`.

- `start` должен совпадать со стартом одного из слотов, которые вернул бы `GET /api/meeting-types/{id}/slots` без учёта занятости: внутри окна записи, в рабочих часах, на шаге стартов, и встреча целиком помещается до конца рабочего дня. Иначе — `400 SLOT_OUT_OF_RANGE`.
- Пересечение с любой бронью любого типа — `409 SLOT_TAKEN`. Проверка и вставка выполняются атомарно (см. [architecture.md](architecture.md)).
- Ответ `201` — полная бронь: `id` (UUID), `meetingType` (`{ id, title }`), `start`, `end`, `guestName`, `guestEmail`, `guestPhone`, `notes`.
- `GET /api/bookings/upcoming` возвращает брони с `end > now` (идущая сейчас встреча тоже предстоящая), по возрастанию `start`, в том же формате.

### Порядок проверок

Бэкенд проверяет `POST /api/bookings` в таком порядке и возвращает первую найденную ошибку:

1. Тело и поля: `400 INVALID_NAME`, `INVALID_EMAIL`, `INVALID_PHONE` или `VALIDATION_ERROR`. Если неверны несколько полей, возвращается код первого в порядке формы: `guestName` → `guestEmail` → `guestPhone` → `notes`.
2. Тип встречи существует: иначе `404 MEETING_TYPE_NOT_FOUND`.
3. `start` совпадает со слотом: иначе `400 SLOT_OUT_OF_RANGE`.
4. Нет пересечения (под `Mutex`): иначе `409 SLOT_TAKEN`.

## Данные гостя

Одно правило на трёх уровнях: `@pattern`/`@minLength`/`@maxLength` в `typespec/main.tsp`, те же паттерны в Kotlin (тест сверяет их с `typespec/openapi.yaml`) и сгенерированная zod-схема на фронтенде (см. [frontend.md](frontend.md#работа-с-api)). В строках TypeSpec обратные слэши удваиваются.

### Имя

```text
^[\p{L}\p{M}]+(?:[ \-][\p{L}\p{M}]+)*$      minLength: 1, maxLength: 100
```

- Слова из букв любого алфавита (с комбинирующими знаками), разделённые ровно одним пробелом или дефисом. Апостроф и точка не допускаются: `O'Brien` и `Jr.` отклоняются.
- Пробелы по краям обрезает фронтенд перед отправкой. Сервер проверяет значение как есть: `" Иван"` → `400 INVALID_NAME`.
- В JavaScript паттерн работает только с флагом `u`. Плагин `zod` hey-api ставит его сам.

### Email

```text
^[A-Za-z0-9!#$%&'*+\/=?^_`\{\|\}~\-]+(?:\.[A-Za-z0-9!#$%&'*+\/=?^_`\{\|\}~\-]+)*@[A-Za-z0-9](?:[A-Za-z0-9\-]{0,61}[A-Za-z0-9])?(?:\.[A-Za-z0-9](?:[A-Za-z0-9\-]{0,61}[A-Za-z0-9])?)+$
```

- WHATWG + dot-atom RFC 5321, до 254 символов, без `format: email`. Принимает `o'neil@example.com` и punycode-домены (`xn--p1ai`). Отклоняет точки по краям и подряд в local-part и домен без точки. Длина local-part (≤ 64) не проверяется.
- Хранится как введён, регистр не меняется.

### Телефон

- Мобильный телефон хранится и передаётся в формате E.164: `+` и код страны, затем номер, без пробелов, скобок и дефисов, не более 15 цифр.
- Регулярное выражение: `^\+[1-9]\d{6,14}$`. Поле обязательное.
- Фронтенд допускает ввод с форматированием и приводит номер к E.164 перед отправкой.

### Заметки

- `notes` — необязательная строка, до 500 символов. Пустая строка приравнивается к отсутствию заметки.
- В ответе ключ `notes` есть всегда: строка или `null`, если заметки нет или она пустая.
- Превышение длины — `400 VALIDATION_ERROR`.

## Ошибки

Любой ответ с ошибкой имеет тело `{ "code": string, "message": string }`, без списка полей. Один код на ответ. `code` — машиночитаемый код из списка ниже, по нему фронтенд показывает перевод. `message` — текст для отладки на английском, пользователю не показывается. В контракте `code` — закрытый enum `ErrorCode`, в SDK ошибка приходит телом без HTTP-статуса, поэтому фронтенд ветвится по `code`.

| HTTP | `code` | Когда |
| --- | --- | --- |
| `400` | `VALIDATION_ERROR` | тело не разбирается как JSON, `notes` длиннее 500 символов, неверны поля типа встречи |
| `400` | `INVALID_NAME` | `guestName` отсутствует, пустое, неверной длины, неверного типа или не проходит паттерн |
| `400` | `INVALID_EMAIL` | `guestEmail` отсутствует, пустое, длиннее 254 символов, неверного типа или не проходит паттерн |
| `400` | `INVALID_PHONE` | `guestPhone` отсутствует, пустое, неверного типа или не в формате E.164 |
| `400` | `SLOT_OUT_OF_RANGE` | `start` не совпадает со слотом: вне окна записи, вне рабочих часов, не на шаге стартов или встреча не помещается в рабочий день |
| `404` | `MEETING_TYPE_NOT_FOUND` | тип встречи не найден, в том числе `id` не UUID |
| `409` | `SLOT_TAKEN` | слот пересекается с существующей бронью |

Это единственный список кодов ошибок. Новый код добавляется сюда, в `ErrorCode` контракта и в оба файла переводов.

Добавление кода не считается ломающим изменением API: `api:breaking` понижает `response-property-enum-value-added` до предупреждения через `scripts/oasdiff-severity-levels.txt`. Удаление или переименование кода — тоже не ломающее для oasdiff, но требует убрать перевод и обработку на фронтенде в том же PR. Код без перевода фронтенд показывает общим текстом `errors.UNKNOWN`.
